# インフラリポジトリのPRを最新の既定ブランチで rebase して競合を解消する

## 依頼内容

人間からの明示的な依頼です。

> {{PR_URL}} がコンフリクトしているので、最新デフォルトブランチでrebaseして解消して。

**対象PR: {{PR_URL}}**
**対象リポジトリとローカルのチェックアウト先は指示ファイルが指定します。** 既定ブランチは `gh pr view` の `baseRefName` で確かめてください。

**やることは競合の解消だけです。** 設計を変えたり、リソースを足したりしないでください。

## 進め方

1. まず `gh pr view <番号> -R <owner>/<repo> --json mergeable,mergeStateStatus,headRefName,baseRefName`
   で**実際に競合しているのかと、基底ブランチが何か**を確認してください。
   綺麗なら、その事実を報告して終わりにしてください（無意味な force push をしない）
2. worktree の場所を `git -C <ローカルのチェックアウト> worktree list --porcelain` で確認する
   - 既存のものを使う前に `git -C <worktree> status -sb` で、**想定どおりのブランチにいて未コミットの変更が
     無いこと**を確認してください。違っていたら、そこを使わず新しい worktree を作ること
     （人間が別用途に使っている可能性があります）
   - **このリポジトリは `~/.config/ai-orchestrator/repositories.json` に登録がありません。** `setupCommand` は無いので、
     `main` から自分で `git worktree add` してください
3. `origin/main` を rebase で取り込み、競合を解消する。**どちらの変更も捨てないこと**
4. force push（自分のブランチのみ）して、MERGEABLE / CLEAN とCIの結果を確認する

## Terraform / インフラ特有の注意

- **`terraform apply` を実行しないでください。** `plan` も、認証やMFAを要求する形では実行しないこと
- **`.tfstate` / `.tfvars` / バックエンド設定に触らないでください**
- 競合が `.tf` のリソース定義なら、**両方のリソースが残るように**解決してください。
  片方のリソースが消えるとインフラが壊れます
- **`terraform fmt` 以外の自動整形をかけないでください**（差分が膨らんで競合の解決内容が読めなくなります）
- モジュールのバージョンやプロバイダのバージョンを**勝手に上げないでください**
- 環境が複数（stg1 / rlststg1 / prod など）に分かれています。**片方だけ直して片方を忘れないよう**、
  同じ変更が要る環境が他にないかを確認してください

## 守ること

- **PRをマージしない**
- **保護対象ブランチ（`main`）へ直接 push しない。** force push は自分のブランチだけ
- **push 前に、現在のリモートの先端を控えておいてください**（やり直せるように）
- PRの文章・コミットメッセージに書いてよい識別子は、そのPRが元から使っている課題管理の識別子だけです。
  **タスクソースの番号やこの仕組みの説明を書かないでください**
- 自分のタスクソース以外の課題管理へは一切書き込まない
- Slackへ書き込まない（読むだけ）
- `.github/workflows/**`、`**/.env*`、秘密鍵の類には触らない
- **認証情報やMFAコードの入力待ちになるコマンドを実行しないでください。**
  過去にこれでセッションが34時間止まりました。要求されたら、そのコマンドは諦めて報告してください
- **force push が権限で拒否されたら、無理に回避せずその旨を報告してください**

## 完了したら報告に含めること

- 実際に競合していたか。していたなら**何がどう衝突し、どう解決したか**（1〜2文）
- PRが MERGEABLE / CLEAN に戻ったこと。CIの結果
- **同じ変更が要る他の環境が無いかを確認した結果**
- **worktree の絶対パス**
- **確かめられていないこと**（`plan` を流していないこと等）。ここは削らないでください

ただし、**やらなくていいと決めてあることは、やっていない報告も要りません。** 規約どおりのPRの `base` や
draft の別、実機での確認は書かないでください。`plan` を流していないことは、流すべきなのに流せていないので書きます。

## 渡す先までステータスを動かす

**担当者を人間へ変えるとき、ステータスを `In Progress` のまま置かないでください。** 人間の画面では
責務ごとに並ぶので、`In Progress` のまま渡されたものはどの列にも入りません。

rebase を通してPRが MERGEABLE に戻ったなら `In Review`、手で解決すべきファイルが多すぎて着手せず
渡すなら `Wait` です。選び方は `impl-from-triage.md`「ステータスも、渡す先まで動かしてください」と
同じで、`Done` / `Canceled` / `Duplicate` へは動かしません。

```bash
npx tsx {{coreDir}}/src/cli/personal-status.ts --id=<ISSUE-ID> --status="In Review"
```
