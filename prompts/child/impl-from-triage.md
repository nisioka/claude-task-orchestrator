# トリアージ済みイシューの実装

**対象イシューの識別子は起動プロンプトで指定されています。**

## まず方針を読む

```bash
cd {{coreDir}}
npx tsx {{coreDir}}/src/cli/personal-issue-detail.ts <ISSUE-ID> --comments=40
```

最新のトリアージコメントに、**原因・修正方針・影響範囲・走っている他案件との衝突・確かめられていないこと**が書いてあります。**これが正式な方針です。設計をやり直さないでください。** 疑問があれば実装しながら確かめ、結論を報告に書いてください。

**コメントに「走っている他案件との衝突」の記述があれば、必ずそれに従ってください。** いま同じメール配信領域で複数の実装が並走しています。

## 作業環境

リポジトリ設定は `~/.config/ai-orchestrator/repositories.json` にあります。**そのリポジトリの `setupPrompt` を先に読んでください。** 作業環境の作り方、検証コマンド、そのリポジトリ固有の落とし穴はそこに書いてあります。`setupCommand` があるときはそれを使ってください。

**worktree の場所を決め打ちしないでください。** `git -C <repo> worktree list --porcelain` で確認してください。

**既存の worktree を名前で再利用する前に `git -C <worktree> status -sb` を見てください。** 人間がブランチを差し替えて自分の作業に使っていることがあります。想定と違うブランチにいる、または未コミットの変更があるときは、**そこを使わず新しい worktree を作ってください。**

ブランチ名は `<type>/<課題識別子の小文字>-<短い説明>`（例 `fix/abc-1234-merge-tag-choice`）。**`auto/` は使わないでください。**

**`git add -A` / `git commit -a` を既定にしないでください。** 変更したパスを明示してステージするのが既定です。リポジトリによっては skip-worktree のローカルパッチが当たっており、巻き込むと壊れます。該当するかは `setupPrompt` に書いてあります。

## 落とし穴（既知。ここで時間を溶かさないでください）

**BE**
- **マイグレーションの採番は `develop` 基準。** make の reorder は staging 基準でズレる。旧名が `build/` に残ると全滅する
- **jOOQ などの生成物を読んで手で直さない。再生成する**
- **`make generate` / `make jooq` は生成物を先に消す。** 途中で落ちると `src/main/kotlin/nu` が消えたままになる。主因はポート衝突
- **テストをローカルで全部通そうとしない**（10時間規模）。`make app/build` まで通してテストはCIに委ねる
- **ktlint は `make app/ktlint` を信じない**（`CD=true` で root 検査が SKIPPED）。**CLI を変更ファイルに直接掛ける**
- **PR には Performance Impact と ANALYZE の記載が要る。** 実装が正しくても書式で赤くなる。**合成データの計測値を根拠に書かない**（未実測なら未実測と書く）
- **compose を make 経由で叩かないと自分のスタックが壊れる**（ポート分離は Makefile の変数計算のため）

**FE**
- **CI は `pnpm lint` の外に stylelint がある。** 生の `4px` のような値を弾き、eslint より前で止まる
- **見た目の確認に `pnpm dev` は使えない**（Auth0 ログインが要る）。**Storybook のハーネス**で確認する
- **BE の DTO を変えると typecheck は `api_client` のピンが進むまで赤い。ポインタを向け直さず、赤いまま報告する**
- rebase 後の typecheck エラーは `.next` の残骸のことがある（`rm -rf apps/*/.next`）
- **`gh pr view --json files` は100件で打ち切られる。** 「そのファイルは無い」と主張する前に `gh pr diff --name-only` で数え直す

## push の叩き方（force push が拒否される原因はここです）

**push は、それ単体で1つのコマンドとして叩いてください。**

```bash
git -C /絶対パス/worktree push --force-with-lease=<branch>:<旧先端SHA> origin <branch>
```

`cd` や変数代入と `;` / `&&` でつなぐ、`$( )` を挟む、`| tail` を付ける — このどれかをやると、
そのコマンドは permission rule と照合されず、**auto mode の分類器の判断に落ちます。** 分類器は
force push をかなりの確率で拒否します（同じ形が通ったり拒否されたりします）。単体の
`git ... push ...` は rule で通るので、分類器を経由しません。

- **`cd` しないでください。** worktree は `git -C <絶対パス>` で指します（Bash ツールの cwd は
  呼び出しごとにリセットされるため、前の呼び出しの `cd` は残りません）
- **パイプ・リダイレクト・`$( )`・変数を混ぜないでください。** push の出力は数行なので `| tail` は要りません
- 旧先端SHA（`git -C <worktree> rev-parse origin/<branch>`）は**別のコマンドで先に取って**、
  値を直接書き込んでください
- 通常の push も同じです（`git -C <絶対パス> push origin <branch>`）
- **それでも拒否されたら迂回しないでください。** 旧先端を `backup/<branch>-<SHA>` に退避し、
  叩いたコマンドをそのまま添えて報告してください

## 制約

- **PRをマージしないでください。** マージは人間の仕事です
- **1リポジトリにつき1つのPRです。工程で分割しないでください。** リポジトリをまたぐときは1リポジトリ1本ずつになりますが、その場合は**両PR本文で互いのリンクを相互参照させ、マージ順を書いてください**
- 基底ブランチを**明示**してPRを作ってください。**下書き（draft）にはしないでください**
- **PRのタイトル・本文・コミットメッセージ・レビュー返信に、タスクソースの番号やこの仕組みの説明を書かないでください。** 参照してよいのは、そのリポジトリの課題管理の識別子だけです
- `.github/workflows/**`、`**/.env*`、秘密鍵の類に触らないでください
- 保護ブランチ（develop / main / master / staging / production）へ直接 push しないでください
- push 前に差分を見て、秘密情報らしき文字列（`xox`・`AKIA`・秘密鍵ブロック）が無いこと、差分が異常に大きくないことを確認してください
- **PR本文の編集は `gh pr edit` が Projects Classic 廃止エラーで失敗します。** `gh api repos/<owner>/<repo>/pulls/<n> -X PATCH -F "body=@file"` を使ってください
- **`gh api` でコメント本文をファイルから渡すときは必ず大文字の `-F "body=@file"` を使ってください。** 小文字の `-f body=@file` は展開されず、**パス文字列がそのまま相手に見える本文として投稿されます**（実際に他人が読むPRへ4件投稿した事故があります）。投稿したら、`gh api repos/<owner>/<repo>/pulls/<n>/comments --paginate` で**自分が投稿した本文を実際に読み返して**確認してください

## 文脈の管理

- **こまめにコミットしてください。** 「全部できてからコミット」にすると、文脈が尽きた瞬間に全部失われます
- **25万トークンに達したら畳んでください**（`/context` で確認）。順番は **(1) コミット (2) push (3) 引き継ぎ**。コミットが先です
- 引き継ぎの書き出し先は `~/.local/state/ai-orchestrator/handover/<ISSUE-ID>-01.md`（既にあれば連番を進める）
- 含めるもの: どこまで終わったか / 今どこを触っているか / 残りは何か / **試して駄目だった方法** / ブランチと worktree の絶対パス / 未コミットの変更の有無 / PRのURL

## 判断に迷ったとき

**聞き返さずに、そのとき最も安全な選択を採って、報告に書いてください。** あなたが止まっている間、誰も先に進めません。

例外は3つだけです。必ず止まって報告してください。

- PRのマージが必要になったとき
- 保護ブランチへの push が要ると判断したとき
- `.github/workflows/**` / `**/.env*` / 秘密鍵に触る必要が出たとき

**「CIを通すために検査の側を緩める」は、常に安全ではありません。** それが唯一の道に見えたら止まって報告してください。

## 終わったら

**やったこと / 検証で実際にやったこと（Storybook で見た、テストを書いた、など）/ 確かめられていないこと / PRのリンク / worktree の絶対パス** を報告してください。**「確かめられていないこと」を省かないでください。**

ただし、**やらなくていいと決めてあることは、やっていない報告も要りません。** 規約どおりのPRの `base` や
draft の別、実機・実際の画面での確認は書かないでください。実機テストは人間の責務です。**書くのは、
やるべきだったのに確かめられなかったことだけです。** 規約から外れたときだけ、外れた事実として書きます。

Storybook のハーネスで見たなら、それは検証の実績なので書いてください。

そのうえで、**Discord へ一報を入れてください。**

```bash
npx tsx {{coreDir}}/src/cli/send-reminder.ts "メッセージ"
```

担当者を人間へ変えれば Linear からも通知は飛びますが、人間が実際に気づくのは Discord です。
**担当者を変えたから Discord は省いてよい、としないでください。**

## ステータスも、渡す先まで動かしてください

担当者を人間へ変えるとき、**ステータスを `In Progress` のまま置かないでください。** 人間の画面では
責務ごとに並ぶので、`In Progress` のまま渡されたものは**どの列にも入らず、何を求められているのかが
分かりません。** 人間が何をする番なのかで決めます。

| 渡す先 | ステータス |
|---|---|
| PRが出ていて、レビューとマージを待つ | `In Review` |
| 判断・仕様・設計を問うている（選択肢を出して選んでほしい） | `Question` |
| 技術的に詰まって介入が要るだけ | `Wait` |

**あなたの作業が終わったかどうかではなく、人間に何を求めているかで選んでください。** 調査だけして
修正を人間の判断待ちにするなら、PRが無くても `Question` です。

```bash
npx tsx {{coreDir}}/src/cli/personal-status.ts --id=<ISSUE-ID> --status="In Review"
```

`Done` / `Canceled` / `Duplicate` へは動かしません（下記）。

## 終了系のステータスへ自分で動かさない

**`Done` / `Canceled` / `Duplicate` へ遷移させないでください。** イシューを終わらせるのは人間です。
あなたが終わらせるのは自分の作業であって、イシューではありません。

重複・対応不要・再現しない、と判断したときも同じです。**根拠をコメントに書いて、担当者を人間へ
変えてください。** 判定が正しくても、閉じるかどうかは人間の裁量です。
